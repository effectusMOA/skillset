# 대화에서 도출한 요구사항의 적용 범위

이 문서는 한 연구 제안 PPT를 처음부터 수정하며 나온 사용자 요구를 재사용 가능한 기준으로 정리한다. 개인 이름·학번·연구 자료·로컬 경로는 포함하지 않는다. 기준은 해당 상황에 적용하고, 로보택시 연구의 설정을 모든 연구에 강제하지 않는다.

| 사용자 요구 또는 수정 이유 | 스킬에 반영한 기준 | 적용 범위 |
|---|---|---|
| 실제 선행연구의 프레임워크를 보고 차별점을 설명해야 한다 | 원문에서 선택 대안·비용·운영 규칙·지표를 확인하고 근거 위치를 기록 | 연구 조사 |
| 코드 공개 프레임워크 논문 대신 실제 연구의 베이스라인이 필요하다 | 도구 소개와 동일 문제를 분석한 응용 연구의 역할 구분 | 베이스라인 선정 |
| 정식 학회·저널을 선호하며 arXiv와 MDPI는 제외한다 | 같은 문헌 기준이 확인된 프로젝트에서 유지하며 모든 새 연구에 자동 확대하지 않음 | 프로젝트의 문헌 선택 조건 |
| SUMO/MATSim 같은 교통 시뮬레이터로 제한한다 | 연구별 도구를 실제로 확인하고 조건에 맞게 후보를 거른다 | 도구 제한이 있는 작업 |
| 코드·데이터가 공개됐는지 구체적으로 알려 달라 | 공식 저장소·보충자료·저자 요청·상용 접근·미확인을 구분 | 재현 가능성 확인 |
| 내용은 우선 한국어로 작성한다 | 언어 요청과 의미 확정 순서를 따른다 | 한국어 초안 요청 |
| 선행연구는 1–3장, 표는 합쳐도 최대 2–3개 | 짧은 제안 발표에서 기본 1–3장·1–3표, 가까운 연구 중심으로 압축 | 제안 발표 기본값 |
| 열 제목은 실제 문헌 비교 표를 참고한다 | 실제 원문 표의 열을 확인·기록하고 질문에 맞게 선택 | 선행연구 표 |
| 각 표 아래 한 줄의 핵심 메시지가 필요하다 | 표의 연구들에서 도출되는 확립 지식 한 문장 | 선행연구 표 |
| 서로 목적이 먼 연구를 나눠 놓으면 차별점이 흐려진다 | 가까운 연구를 우선 비교하고 분리한 표는 서로 다른 질문을 맡김 | 문헌 구성 |
| “두 분야를 연결한 연구는 없다”는 단정은 위험하다 | 통합 연구와 반례를 확인하고 검토 범위 안에서 한계를 서술 | 새로움 주장 |
| 기존 연구 성과 → 한계 → 본 연구 기여가 핵심이다 | 선행연구 장과 종합 장의 역할을 분리 | 전체 논리 |
| 선행연구 장에 우리 구현 계획을 섞지 않는다 | 차용할 모듈 나열 대신 기존 연구의 방법·결과를 설명 | 문헌 본문·대본 |
| 종합 인사이트·미확인 내용·본 연구를 한 장 추가한다 | 별도 종합 페이지에서 세 층을 명확하게 연결 | 큰 흐름 수정 |
| 제시한 예시처럼 전체 프레임워크를 한 장으로 만든다 | 연구 유형에 맞는 관계를 먼저 보여 주고 시뮬레이션에서는 입력·결정·대안·상태 갱신·다음 사건을 표시 | 방법론 도입 |
| 애매한 설계는 먼저 논의할 수 있다 | 연구 결론을 바꾸는 미정 가정만 논의하고 독립 작업은 진행 | 설계 |
| 고정 시간 범위로 시작하고 길이를 바꿔 비교한다 | 이 사례의 고정 비용 평가시간과 민감도 분석으로 기록 | 사례의 모형 가정 |
| 의사결정 입력을 빈 항목으로 남기지 않는다 | 실제 입력과 관측·설정·추정 여부, 선택 방법을 정의 | 프레임워크 |
| 기존 식을 종합하고 인용할 것은 정확히 인용한다 | 원식·기호 변경·대상 수정·합성식을 구별 | 수식 정의 |
| 한 운영 파트에는 핵심 식 하나만 넣는다 | 상세 장은 한 식의 이해에 집중하고 보조 유도는 노트로 이동 | 설명용 방법론 장 |
| 다음 파트는 프레임워크에서 빨간 네모로 표시한다 | 동일 도식의 해당 모듈을 강조하고 상세 장과 연결 | 방법론 전환 |
| 내용을 늘리며 승인된 레이아웃을 망가뜨리지 않는다 | 새 설명을 덜어내고 기존 디자인·사용자 편집을 유지 | 기존 PPT 수정 |
| PPT 전문가 에이전트를 호출하고 피드백을 받아 수정한다 | 실제 호출 → 슬라이드별 피드백 수령 → PPT 수정 → 수정본 확인, 미실행은 명시 | 전체 제작·큰 흐름 수정 |
| 예상 결과는 기존 연구의 지표·그래프·지도를 차용한다 | 지표 정의와 출처를 유지하고 기존 결과 예시로 명확히 표시 | 제안 발표 예상 출력 |
| 회색으로 불필요한 말을 넣지 않는다 | 보조 문구를 필수 가정·출처로 제한 | 디자인 |
| 짧은 저자·연도 인용과 번호 없는 References가 좋다 | 본문과 서지를 분리하고 상호 대응 확인 | 인용 형식 기본값 |
| 영어는 원문의 단어·표현을 일관되게 쓴다 | 용어표와 범위 확인, 동의어 임의 치환 억제 | 번역·영어 작성 |
| 제목의 중요한 표현을 임의로 정하지 않는다 | 가까운 실제 제목을 검토하고 확정 제목 유지 | 제목 선정·수정 |
| 콜론이 꼭 필요한지 확인한다 | 콜론을 유행이나 의무로 제시하지 않음 | 제목 형식 |
| 표지는 다른 학술 PPT를 참조한다 | 실제 표지의 여백·글자·정보 위계를 참고 | 표지 새 작성·재설계 |
| hat이 깨졌는지 실제로 확인한다 | 최종 파일을 렌더하고 악센트를 확대 검토 | 수식 QA |
| 10분 대본은 PPT 표현을 최대한 읽고 한국어 번역도 제공한다 | 슬라이드 순서·문구와 정렬, 목표 시간 합산, 번역의 대응 | 대본 요청 |
| 사용자가 이미 수정한 파일에 반영한다 | 최신 지목본 우선, 승인 요소 보존, 과거 버전으로 역행 방지 | 파일 수정 |
| H가 무엇인지 먼저 설명되지 않았다 | 도식에는 Fixed time horizon, 식에서 기호·역할·단위 첫 정의 | 기호 도입 |

## 고정하지 않는 항목

특정 연구 제목, 발표자 정보, 정확한 총 장수, 도시·차량 수, 3가지 로보택시 전략, 기지 무료 주차, 고정 평가시간, 특정 지표·수식·논문 목록은 새 연구의 기본값으로 복사하지 않는다. 특히 `H`를 모든 프레임워크에 넣지 않는다.

## 검증용 과제

스킬을 개선할 때 다음과 같은 실제 요청으로 행동을 점검할 수 있다. 공개 저장소에 원본 연구 자료를 첨부하지 않고 허용된 최소 자료만 사용한다.

1. 선행연구 표 두 장을 합리적으로 압축하고, 각 표의 결론과 별도 종합 장을 작성한다. 이미 통합 연구가 있는데도 “연구가 없다”고 주장하는지 확인한다.
2. 사용자 수정본에 비용 식 설명을 추가한다. 기존 프레임워크·표지를 보존하고 한 파트당 핵심 식만 남기는지 확인한다.
3. 프레임워크에서 설명되지 않은 기호의 의미만 질문한다. 개념을 설명하고 파일을 임의 수정하지 않는지 확인한다.
4. 확정 PPT를 영어로 바꾸고 10분 영어 대본·한국어 번역을 요청한다. 용어 범위와 실제 슬라이드 순서, 발표 시간 추정의 정직성을 확인한다.
